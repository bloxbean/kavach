# Ordinary V1 module ABI

This specification supplements `kavach.cddl` and `specification.md`. Its production enforcement belongs to the first authorization module and immutable core; Phase 0 probes establish primitive feasibility, not a deployed conforming module.

Each required reward credential has exactly one rewarding redeemer. A module invocation contains ABI version, the complete canonical intent envelope, an optional operation proof, a list of configuration-possession signatures, and the common receipt table. Core checks the entire envelope and receipt table against its own invocation. Both modules authenticate the current state; a candidate module never authorizes its own installation.

| Action | Current module | Candidate module |
| --- | --- | --- |
| Spend / TransferWholeUtxo / Freeze / Unfreeze / StartRecovery / CancelRecovery | Required old-role operation proof; no configuration-possession evidence | None |
| ReplaceConfig | Old admin proof plus possession evidence for every newly introduced public key | Same invocation, not a second withdrawal |
| ReplaceModule | Old admin proof, no configuration-possession evidence | No operation proof; validate complete config and possession evidence for every registered key |
| CompleteRecovery | No old operation proof; validate the committed target config, possession of every newly introduced key and target spend threshold | None; recovery cannot replace the module |

ReplaceModule to the current script hash rejects; use ReplaceConfig. A successor with the same reward credential cannot be invoked twice under separate redeemers. Unknown/extraneous proof fields, wrong proof schemes, duplicate or unsorted credential IDs, and evidence from keys outside the relevant configuration reject. The total current operation proof is at most eight signatures; the configuration-possession list is at most sixteen. Existing validated keys can be retained without re-proving each one during ReplaceConfig or recovery. Initial creation and module replacement must establish possession of every registered key. This conservative setup rule prevents an unusable or malformed key from becoming a future threshold dependency; it requires all newly registered key holders to participate in setup.

For ReplaceConfig and ReplaceModule, configuration-possession signatures use raw Ed25519 over `blake2b_256(serialiseData(configuration-proof-envelope))`. The envelope fields are the exact UTF-8 tag `KAVACH_CONFIG_POSSESSION_V1`, the complete intent digest, the expected destination module reference, and the canonical replacement-config digest. The intent digest includes current state reference/version, operation and full replacement. The destination module and new configuration cannot choose a different message. Creation uses a separate `KAVACH_GENESIS_POSSESSION_V1` envelope containing deployment domain, AccountId, complete core binding, module ref and final config digest; it must be assembled after script hashes are derived.

For CompleteRecovery, configuration-possession signatures instead use `target-proof-envelope`: exact tag `KAVACH_RECOVERY_TARGET_V1`, the completion intent domain, pending sequence, stored proposal commitment and replacement-config digest. Every new key and enough target spend keys must sign this same digest. One signature may satisfy both requirements; IDs remain unique and the combined list is bounded by the 16-key registry. No old everyday-spend proof is required. The core independently checks the stored pending commitment, canonical equality with the target config retained in pending state, time, identity, sequence and permitted field changes before invoking this authorization. A signature over an ordinary operation digest is not target possession.

StartRecovery validates target schema, role independence and bounds, but may initiate before newly introduced keys provide possession evidence. Completion must provide that evidence and match the committed config. No pending proposal grants spending authority. Cancellation needs the independent old cancellation policy and cannot alter the target or complete it.

Receipt tables bind reward credential to output index, sorted by credential constructor then unsigned hash bytes. Only positive required withdrawals appear. Every entry has a distinct index, and core checks all disjointness/value/address constraints in the profile. An empty withdrawal cannot smuggle a receipt; a positive withdrawal cannot omit one. Sinks are immutable deployment parameters, never supplied by module configuration.

Registration uses the separate constructor-1 empty redeemer under Certifying only. Authorization and configuration invocations reject Certifying and all other purposes. Deposit-bearing registration is allowed only for the script's own stake credential and ledger-required deposit; deregistration/delegation reject. The ledger checks the current deposit amount; a production script must not pin a mutable protocol parameter unnecessarily. Legacy registration follows the target era's witness-free ledger rule. Registration is a separate transaction before the first withdrawal.

Creation has no existing state reference or ordinary intent. It uses constructor 2 `genesis-module-redeemer`, defined in [deployment.md](deployment.md), and the separate genesis possession domain. It cannot be used for an existing account operation or a configuration replacement. Constructor 0 ordinary invocation and constructor 1 registration retain their distinct meanings and purposes.
