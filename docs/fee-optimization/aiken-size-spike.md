# Aiken port: size, execution and behaviour against JuLC

Status: **comparison port of all twelve production validators, not a second qualified protocol
implementation.** Nothing here is deployed, audited or ledger-validated, and no Java contract, wire
schema, script hash or toolchain pin changes. Evidence:
[aiken-size-spike.json](evidence/aiken-size-spike.json) (template sizes) and
[aiken-port-comparison.json](evidence/aiken-port-comparison.json) (behaviour, execution budgets,
applied sizes, fee estimate), both regenerated by `./gradlew aikenPortComparison`.

## The question

[The script size analysis](script-size-analysis.md) found that an ordinary transfer attaches three
reference scripts totalling more than one 25,600-byte Conway tier, that fitting one tier needs about
a 30% reduction, and that JuLC-side representation work recovers about 7%. A different compiler was
the remaining candidate. The threshold set before measuring was **1.50x** smaller transfer scripts.

## Headline

| | JuLC `0.1.0-pre17-6754861` | Aiken `v1.1.23` + stdlib `v2.2.0` | |
| --- | ---: | ---: | ---: |
| Ed25519 transfer scripts, applied bytes charged | 36,091 | **28,684** | 1.26x |
| bytes over one 25,600-byte tier | 10,491 | **3,084** | |
| estimated ordinary transfer fee | 1.0734 ADA | **0.9661 ADA** | −0.107 ADA (−10%) |
| suite evaluations with the same accept/reject outcome | | **813 of 813** | |
| contract tests passing | 314 of 314 | **309 of 314** | |
| largest transfer profile within `max_tx_ex_mem` | yes | **no** | |

1. **Aiken does not reach one tier.** The transfer scripts are 1.26x smaller, not 1.50x. They still
   pay 3,084 bytes at the second-tier rate.
2. **It would save about 0.107 ADA per ordinary transfer.** The reference-script fee falls by
   133,326 lovelace, and 26,031 lovelace of that comes back as higher execution cost. That is
   roughly twice the 0.048 ADA an upstream JuLC CSE pass is estimated to save.
3. **The port as written cannot execute Kavach's largest supported operations in one transaction.**
   The maximum transfer profile and the 16-key module replacement exceed the per-transaction
   execution limits. This is the finding that matters most: a smaller script that cannot run the
   supported profile is not a drop-in replacement.
4. **No behavioural divergence was observed.** Every accept/reject outcome in the existing
   compiled-contract suite matched, across all twelve validators substituted at once.

### Maximum profiles exceed the per-transaction limits

Totals include the SDK's 5% allowance, against `max_tx_ex_mem` 16,500,000 and `max_tx_ex_steps`
10,000,000,000.

| profile | JuLC memory | Aiken memory | JuLC CPU | Aiken CPU |
| --- | ---: | ---: | ---: | ---: |
| 8+8 inputs, 16 outputs, 12 native entries | 13,354,509 | **19,076,632** | 6.53 B | 8.29 B |
| same, positive rewards | 13,990,410 | **19,322,779** | 6.74 B | 8.45 B |
| same, eight recipients | 13,853,167 | **20,834,295** | 8.12 B | **10.41 B** |
| same, positive rewards and eight recipients | 14,360,227 | **21,490,093** | 8.30 B | **10.69 B** |
| 16-key module replacement | 14,916,116 | **17,466,509** | 9.60 B | **10.78 B** |

These are the five failing tests. Where the cost comes from, as far as the budgets show without
per-builtin profiling:

- **Value aggregation.** The maximum anchor input costs 3.48 B CPU and 10.89 M memory in Aiken
  against 2.22 B and 6.57 M in JuLC. JuLC's `NativeAccountingLib` uses the PV11 native-Value
  builtins; Aiken v1.1.23 does not expose them, so the port aggregates with stdlib `assets.merge`
  and tuple-accumulating folds. This is mostly a toolchain capability gap, not code generation.
- **Typed decoding.** A non-anchor asset input does nothing but read the checkpoint redeemer and
  compare the binding. It costs 1.44x the memory in Aiken (261,486 against 181,440), which isolates
  the cost of the typed `expect` decode on that path. The checkpoint and modules decode
  `CoreRedeemer`, `ModuleInvocation` and configurations the same way.

The JuLC sources have been through the [fee-optimization review](review.md). The Aiken port has had
no execution-cost pass, so these numbers compare a tuned implementation with a first one.

## How behaviour was compared

`-PaikenContracts=all` (or a comma-separated list of JuLC class names) makes the test fixtures load
the Aiken blueprint's code instead of the JuLC validator, applied with the same parameters in the
same order. Every compiled-contract test in `com.bloxbean.cardano.kavach.contracts` then runs
unchanged against the Aiken scripts, including the adversarial, shape, lifecycle, recovery,
transfer, whole-transfer, browser, policy, mixed-setup and budget suites. Each evaluation's outcome
and budget is logged, and the JuLC and Aiken logs are compared entry by entry. The substitution is
confined to the unit `test` task and the comparison tasks, so it can never reach DevKit tasks or
qualification evidence. In Aiken mode, `AccountBudgetTest` writes its budget files under
`build/fee-optimization/aiken-port`, never `build/phase1`.

What this does and does not establish:

- It compares **outcome class only**: both accept, or both reject. It does not compare why a
  rejection happened; an Aiken script may fail on a typed decode where JuLC returns false later.
- Coverage is exactly the existing suite's. The tests were written for JuLC, so paths reachable only
  through Aiken-specific behaviour are not separately targeted.
- Contexts are fabricated and evaluated in JuLC's Java VM at PV11, not by `cardano-node`. No Aiken
  script has been submitted to a ledger.

Wire parity is proven separately: `wire_conformance.ak` rebuilds `conformance/v1/state.hex` from the
Aiken types and requires `serialise_data` to reproduce it byte-for-byte and its Blake2b-256 digest to
match.

## Where the two implementations necessarily differ

- **PV11 native-Value builtins** are absent from Aiken v1.1.23. Accounting uses stdlib Value
  functions, which produce the same canonical results on ledger-supplied values. The asset
  validators therefore compare stdlib Value code against builtins, not compilers alone.
- **PV11 array builtins** are absent. List sizes use `list.length`, which is linear rather than
  constant-time.
- **Registration deposit.** The stdlib types `RegisterCredential.deposit` as `Never`, noting that
  the ledger has supplied `None` even when a deposit is set. The Java requires the deposit to be
  present, so `certify` reads the certificate as raw `Data` to keep that check. Whether the pinned
  ledger supplies the deposit to a script is unverified. DevKit tests register stake addresses
  without executing `certify`, so no ledger evidence exists either way.
- **Typed decoding.** Where the Java casts `Data` without checking it, the port uses `expect`, which
  validates structure. The Java's explicit `shape` and rebuild-and-compare checks are kept too, so
  much of that structure is validated twice. Aiken may therefore reject malformed input by error
  where JuLC returns false; no such difference appeared in the suite. An earlier version of this
  document said Aiken "validates strictly more", which overstated it.
- **Structure mirrors the Java.** The four lifecycle libraries, the budget copies of the spend and
  whole-transfer libraries, and each module's `bound` are kept separate, as in the Java. There is no
  Aiken-specific restructuring.

## What this means

- **For the fee question: no single tier, about 10% cheaper ordinary transfers.** Aiken is 3,084
  bytes (10.8%) short of one tier on the Ed25519 transfer set. The estimate uses fixture budgets for
  a three-key account with one recipient and the recorded Phase 2 base fee, not a DevKit
  measurement.
- **The port cannot replace JuLC as it stands,** because Kavach's largest supported transfer and
  module replacement would not fit in a transaction. Making it fit needs an execution-cost pass,
  mainly on value aggregation. That pass is unmeasured and could move the size figures either way.
- **The remaining gap to one tier is not obviously closable.** Replacing typed decodes with raw
  `Data` access would save bytes and execution, but it gives up the structural checks that are
  Aiken's safety advantage, and its effect on the transfer set has not been measured.
- **Switching implementations is a separate decision** with its own ADR. It would double the
  security surface and require the full qualification AGENTS.md sets for contracts: adversarial
  suites, execution-budget coverage, DevKit ledger validation and review. This comparison supplies
  inputs to that decision, not the decision.

## State validator detail (from the single-validator spike)

For `AccountStateValidator`, Aiken emits 18% fewer UPLC terms but only 4% fewer bytes, with 50%
more distinct subterms; its largest repeated subterm is 144 bytes against JuLC's 304. Aiken already
shares common subexpressions, which `UplcOptimizer` does not. JuLC's measured CSE headroom on that
validator is 261 bytes, which would bring the two close to a tie. `probe.ak` measures the typed
decodes in isolation: `CoreRedeemer` 1,470 bytes and `AccountState` 481 bytes over a 98-byte raw
baseline.

The spike's "1.40x like-for-like upper bound" applied to that one validator only. Measured
whole-port figures supersede it.

The CDDL was sufficient to write every Aiken type. `tx-out-ref` is the flattened Plutus V3 form,
which is exactly Aiken's `OutputReference`, so signed intent domains are compatible across the two
implementations.

## Pinned versions

`aiken.toml` fixes the compiler at `v1.1.23` and the stdlib at `v2.2.0`; `aiken.lock` records the
resolved stdlib. Generated code differs across stdlib majors, so a different pair is a different
measurement. `./gradlew aikenSizeSpike` refuses any other compiler version. Output uses the default
silent trace level, matching JuLC's traceless emission.

## Reproduce

```sh
./gradlew aikenPortComparison      # builds the port, runs the suite twice, writes both evidence files
./gradlew test -PaikenContracts=all                       # the suite against every Aiken script
./gradlew test -PaikenContracts=CoreCheckpoint,AccountAssetValidator   # or a subset
```

`aikenPortComparison` tolerates the Aiken run's five budget-ceiling failures and lists them in the
evidence. None of these tasks is part of `check`.
