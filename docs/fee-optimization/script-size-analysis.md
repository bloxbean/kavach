# Compiled script size: where the bytes are

Status: measurement only. No contract, wire schema, script hash or toolchain pin changes here.
DevKit figures from the pinned `0.1.0-pre17-6754861-SNAPSHOT` toolchain; not a production
deployment or audit claim.

Evidence: [script-size-analysis.json](evidence/script-size-analysis.json), regenerated by
`ScriptSizeAnalysisTest`. It writes to `build/fee-optimization/` and preserves prior evidence.

## Why this was measured

Reference scripts are charged twice. Conway charges their total size per transaction in tiers of
25,600 bytes, the second tier at a 1.2x multiplier; and each publication locks
`coinsPerUtxoSize x (serialized bytes + 160)` as its ledger minimum. A browser-module transfer
attaches about 36,973 bytes of reference script once parameters are applied, so it pays the first
tier in full plus 11,373 bytes at the higher rate — 588,714 lovelace of its roughly 1.02–1.2 ADA
fee, about half. Cutting those 11,373 bytes would save 204,714 lovelace, about 0.205 ADA, on every
transfer.

Figures below are **unapplied templates** unless stated otherwise, because that is what the
compiler emits and what a compiler change would move. Applying parameters adds a few hundred bytes
across the graph: the three transfer scripts measure 36,408 as templates and about 36,973 as
charged. Comparisons are template-to-template throughout.

That is the prize. This document records whether it is reachable.

## The headline

**It is not reachable by representation-level change.** A single tier needs a **29.7%** reduction on the transfer path
(30.8% on the charged applied bytes). Every mechanism found here totals at most 7%, and the three attached scripts
are all genuinely executed, so none can simply be dropped. Reaching one tier would require changing
what the protocol executes during a transfer, not how it is compiled.

## Findings, ranked

### 1. The toolchain upgrade cost nothing; the growth since fee optimization is features

The fee-optimization review's build manifest recorded asset + checkpoint + Ed25519 module
templates at 30,972 bytes, charged as 31,440 applied. The same three templates today are 35,638.
That 4,666-byte growth is **entirely Kavach source growth**, not a compiler regression.

Building today's source with the *previous* pinned toolchain `0.1.0-pre17-1a46882-SNAPSHOT`
produces byte-identical output to `6754861` for all five reference scripts. The serialization-fix
upgrade changed no emitted byte.

| script | fee-opt source, old julc | current source, old julc | current source, new julc |
| --- | ---: | ---: | ---: |
| AccountAssetValidator | 10,569 | 10,559 | 10,559 |
| StateNftPolicy | 6,007 | 5,701 | 5,701 |
| CoreCheckpoint | 8,004 | 10,484 | 10,484 |
| Ed25519Module | 12,399 | 14,595 | 14,595 |

Two scripts did not grow at all. `CoreCheckpoint` (+2,480) and the authorization module (+2,196)
carry the Phase 2 lifecycle, recovery, budget and whole-transfer work added after that review.
These bytes bought capability; they are not waste to reclaim, and removing them removes features.

The `AccountStateValidator` row of that historical manifest reads 32 bytes because it predates the
real state validator. It is not comparable and is excluded above.

### 2. Compiler optimization level: already maximal

The annotation processor accepts `julc.optimization` with levels `none`, `baseline`, `pv11-safe`
and `pv11-costed`. Kavach configures none, so it gets the default `pv11-safe`. Compiling every
script at `pv11-costed` with the pinned `cardano-node-11.0.1-plutus-v3-pv11` cost profile produces
**byte-identical output** — its extra cost-justified rules do not fire on this code. There is no
free compiler setting left.

### 3. Upstream: the Z combinator is emitted inline at every recursive binding

The single largest redundancy is not Kavach's. `UplcGenerator.generateLetRec` emits the Z fixpoint
combinator `\f -> (\x -> f (\v -> x x v)) (\x -> f (\v -> x x v))` inline at **every** recursive
binding, and no pass in `UplcOptimizer` — force-delay-cancel, constant-fold, exp-mod-literal,
dead-code-elimination, beta-reduce, eta-reduce, constr-case-reduce — hoists it. There is no common
subexpression elimination pass at all.

| script | occurrences | recovered by hoisting |
| --- | ---: | ---: |
| AccountStateValidator | 17 | 261 |
| CoreCheckpoint | 44 | 707 |
| BrowserModule | 52 | 837 |
| StateNftPolicy | 22 | 344 |
| AccountAssetValidator | 35 | 557 |
| **total** | **170** | **2,706 (5.4%)** |

The rewrite is sound, and the test proves it rather than asserting it: substituting the combinator
back into the hoisted body reproduces the original term byte-for-byte on all five scripts. The
transform is therefore exactly a beta-expansion of a **closed value**, which cannot capture a
variable, duplicate work or reorder an error.

Extending the same hoist to every closed repeated subterm recovers **at least 3,510 bytes (7.0%)**.
That figure comes from one greedy selection of 40 candidates and is a lower bound on what a real
CSE pass would achieve, not a ceiling.

Constant folding would be a simpler upstream fix covering part of the same ground:
`AccountAssetValidator` builds `constrData 0 (mkNilData ())` 73 times and the tag-1 form 74 times,
each a compile-time-known `Data` value that `constantFold` does not currently fold.

**This is upstream JuLC work.** Kavach cannot adopt it without a new toolchain pin, and AGENTS.md
forbids rewriting emitted UPLC to get the benefit locally. The test here never emits a rewritten
program; it only measures one.

### 4. Off-chain attachment is already minimal

A transfer attaches exactly the three scripts it executes: `AccountAssetValidator` as the spending
validator, and `CoreCheckpoint` and the authorization module as withdraw-0 reward validators. The
state UTxO is only `readFrom`, so the state validator neither executes nor is attached, and no
minting happens, so the NFT policy is absent. `ScriptSizeAnalysisTest.transferAttachesOnlyExecutedScripts`
pins that correspondence.

Scripts are also not paid for twice. The recorded spend transaction is **1,617 bytes**; had the
witness set carried the scripts inline alongside the reference inputs it would exceed 36,000.
`DuplicateScriptWitnessChecker.removeDuplicateScriptWitnesses` is doing its job.

### 5. Execution allowance: deliberate, and not worth touching

`ExecutionBudgetMargin` adds a documented 5% allowance over each measured redeemer budget.
Execution is roughly 308,000 lovelace of the transfer fee, so the entire allowance is about 0.015
ADA. Removing it trades transaction reliability for a rounding error, and the fee-optimization
review already records the 5% allowance as unchanged. Left alone.

## What a reduction would actually cost

Any change to emitted bytes changes script hashes, and per ADR-001 core upgrades do not preserve
addresses. So every item above that could move bytes is a protocol version bump: new addresses,
fresh adversarial rejection cases, execution-budget coverage, conformance fixtures and a re-pinned
toolchain manifest. Existing accounts cannot migrate to it.

Adopting an upstream CSE pass would buy roughly 0.048 ADA per transfer and about 11.4 ADA less
locked per account — and under ADR-011 that deposit is reclaimable float, not burn, so the deposit
half of the saving is a float reduction rather than a cost reduction. Whether that justifies a
version bump is a decision for the acceptance ledger, not for this measurement.
